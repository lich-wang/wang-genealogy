# 协作、版本与合并机制

## 一、Wiki 式维护，不等于最后写入者获胜

系统允许多人维护同一个人物，但页面摘要由主张状态和来源共同生成。不同资料互相矛盾时，可以同时保留：

```text
主张 A：某人生于 1021 年，来源一、来源二，状态 accepted
主张 B：某人生于 1020 年，来源三，状态 disputed
```

页面可以显示推荐值，但不得隐藏仍有有效来源的少数意见。

## 二、修改记录

每次操作形成不可变贡献记录：

- 创建人物；
- 新增主张；
- 修改主张；
- 新增或移除来源关联；
- 标记争议；
- 撤回或回滚；
- 发起、执行或撤销人物合并。

贡献记录至少包含操作者、时间、修改摘要、修改前后版本和影响对象。

运维层面的归属调整（`admin.reattribute`，例如把导入账号产生的记录改归站点所有者）同样写入这条流水：只改归属字段，不改主张内容、状态和版本。

## 三、人物维护机制

用户可以关注或申请维护人物。维护者的作用是：

- 接收修改通知；
- 参与审核争议；
- 协助确认重复人物；
- 改善来源和说明。

维护者不得：

- 删除有可靠来源但自己不认可的观点；
- 宣称对公共历史人物拥有排他控制权；
- 以宗族身份替代文献证据。

## 四、重复人物发现

候选匹配可以根据以下信息提示，但不能自动合并：

- 姓名及异名（**字形折叠后比较**：「王賁」与「王贲」按同名处理，避免同一人因简繁差异被录入两次）；
- 人工选择同名人物时同时核对生卒、籍贯、支派、字／号与已有亲属，不以姓名或内部 ID 单独判断；
- 先祖／后代关系只有在来源明确给出时才填写 `generation_count`；「四世孫」记为 `4`，仅能确认世系时留空，相隔一代改用父母／子女关系；
- 来源明确写父亲或母亲时选择 `father`／`mother`；只写「父母」「双亲」或无法判断时使用 `parent`，不按姓名猜测；
- 生卒区间；
- 谱籍地和迁居地；
- 父母、配偶、子女；
- 所属支派、堂号、字辈；
- 外部数据库 ID。

## 五、软合并流程

1. 选择两个疑似相同人物。
2. 并列展示全部属性、关系、来源、维护者和冲突。
3. 贡献者提交合并理由及支持主张。
4. 系统计算受影响的关系数量，并检测循环或自关系。
5. 满足简化条件时由同时维护两条记录的用户确认；否则进入审核。
6. 执行事务性软合并：
   - 源人物状态改为 `merged`；
   - 旧 ID 指向目标 ID；
   - 主张和来源保留原始创建记录，同时增加规范目标引用；
   - 完全重复主张只做逻辑折叠，不物理删除；
   - 生成完整合并快照。
7. 所有旧链接继续工作。

## 六、合并后的冲突

合并人物的资料可能并不一致。合并只表示“这两个 ID 指向同一历史人物”，不表示所有主张同时正确。冲突主张继续保留并进入争议处理。

## 七、撤销合并

撤销必须基于原合并快照：

- 恢复源人物；
- 恢复合并前主张归属；
- 保留合并及撤销的审计历史；
- 对合并期间新增的主张逐条确定归属，不能静默丢弃。

## 七之二、同名异人：一条记录拆成两条

字形折叠让「王賁」和「王贲」按同名处理，代价是把两个真正的同名者也并成一个。史料越简，代价越高：《新唐書·宰相世系表》通篇只写单名，「錯生賁」的賁与「翦生賁」的賁相隔七代，按名字匹配就成了同一人，一条世系于是首尾相接。

服务端的环检测只拒绝**闭合**那个环的那条边。前面每一条边看上去都是两个真人之间的合法关系，会被逐条写入，最后剩下一段已经折叠的世系，加上一条指错对象的拒绝信息。因此：

- **导入前先找环，不要等服务端逐条拒绝。** 在「已有世系边 + 本次计划的世系边」构成的图上求强连通分量，落在同一分量里的计划边整批跳过，并把整个分量按人名打印出来（`scripts/lib/loops.mjs`）。哪个名字其实是两个人，是人来判断的事。
- **拆分动作见 `docs/DOMAIN_MODEL.md`「一条记录其实是两个同名的人」**：新建 → 撤回 → 用同一条引用改挂，顺序不可颠倒。
- **拆分需要审核者判断，不进自动流程。** 与合并提案一样，同名待查项只作提示，不自动执行。

## 八、术语说明

批量人物资料计划只新增当前缺失的属性，整批必须带支持来源并由管理员或维护者提交。若任一人物、来源或同谓词主张与计划不符，接口拒绝整批，先重新审计再提交；不得以覆盖现值的方式追求字段完整率。

当前设计中的“合并”是合并重复的历史人物记录，不是合并贡献者登录账号。账号合并如未来确有需要，应作为独立安全功能设计。
